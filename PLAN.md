# План переноса MotifHORDE на Julia

## Цель и границы

Цель -- заменить Python-пакет `motifhorde` на нативный Julia-пакет
`MotifHORDE.jl`, сохранив назначение, алгоритм отбора и пользовательский
контракт CLI. Конечный пакет не должен зависеть от Python, `mimosa-tool`,
`pybind11`, C++-расширения `sitega` или PythonCall.

`Mimosa.jl` является единственным runtime для представления, чтения, записи,
сканирования, сравнения и преобразования моделей. До начала реализации нужно
зафиксировать его фактический публичный API и поддерживаемые форматы по
репозиторию [Mimosa.jl](https://github.com/ubercomrade/Mimosa.jl), а не
переносить предположения из Python API.

SiteGA становится отдельным Julia-проектом. В `MotifHORDE.jl` остаётся
`SitegaDiscoveryTool` как адаптер внешнего процесса; алгоритм обучения SiteGA
и его исходный код не входят в этот репозиторий.

Во время переноса Python-реализация служит только нераспространяемым эталоном
поведения на migration branch. Новый релиз возможен только после полного
удаления Python-кода, Python-тестов, Python build/runtime-зависимостей и C++
SiteGA из поставляемого репозитория. Не следует поддерживать два production
runtime, выпускать переходный Python/Julia-релиз или добавлять новые функции в
Python/C++ SiteGA.

## 1. Зафиксировать контракт и эталон

1. Описать versioned compatibility matrix для текущего CLI: обязательные
   аргументы, значения `--tool`, диапазоны параметров, валидацию, коды выхода,
   переменные окружения и уровень логирования.
2. Зафиксировать структуру результатов: каталог `<output>/<tool>/`, bootstrap
   статистику, финальную статистику, имена мотивов, порядок мотивов и
   `all_motifs_in_pfm_form.meme`.
3. Сохранить существующие малые FASTA-файлы и unit fixtures как независимые
   тестовые данные. Создать эталонные результаты Python для детерминированных
   fake discovery tools и для доступных внешних инструментов.
4. Для каждого наблюдаемого результата определить правило сравнения: точное
   совпадение для имён, параметров, выборок, JSON и дискретных решений;
   численная допусковая проверка для floating-point оценок и профилей;
   сравнение инвариантов, а не байтов, для недетерминированного обучения.
5. Зафиксировать разрыв с Python-артефактами. Python `joblib`/pickle не
   является переносимым форматом; Julia-релиз не читает и не создаёт его.
   Модели для нового runtime регенерируются из исходного вывода либо
   экспортируются в поддерживаемый Mimosa.jl формат; compatibility loader не
   создаётся.

Критерий выхода: контракт, fixtures и правила сравнения лежат в репозитории и
дают воспроизводимый baseline для всех поддерживаемых инструментов.

## 2. Подтвердить интеграционные границы

1. Создать изолированный Julia spike-проект и установить Mimosa.jl через
   `Pkg`; зафиксировать совместимую версию или ревизию в `Manifest.toml`.
2. Проверить на реальных fixtures весь необходимый API Mimosa.jl:
   FASTA/последовательности, `GenericModel`-эквивалент, чтение и запись,
   сканирование обеих цепей, пороги, сайты, PFM, профильное сравнение,
   matrix/Tomtom-like сравнение и null distribution для adjusted p-value.
3. Составить format matrix для `pwm`, `bamm`, `dimont`, `slim`, `sitega` и
   `scores`: входной формат discovery tool, reader Mimosa.jl, stable output
   format и отсутствующие возможности. Пробелы закрывать в Mimosa.jl, а не
   локальными дублирующими parser/scanner реализациями.
4. Согласовать с отдельным проектом SiteGA стабильный process contract до
   реализации адаптера. Он должен включать команду, версию, machine-readable
   manifest, модельные файлы, коды ошибок и детерминированность при seed.
5. Проверить, что SiteGA выдаёт формат, читаемый Mimosa.jl. Если это невозможно,
   сначала определить и реализовать форматную границу в соответствующем
   проекте; MotifHORDE не должен знать внутреннее представление SiteGA.

Критерий выхода: есть небольшие Julia integration tests, доказывающие каждую
нужную операцию Mimosa.jl и round-trip будущего SiteGA без Python.

## 3. Создать каркас Julia-пакета

1. Инициализировать стандартный пакет `MotifHORDE.jl` через `Pkg` с
   `Project.toml`, `Manifest.toml`, `src/MotifHORDE.jl`, `test/runtests.jl` и
   документацией запуска. Не редактировать `Project.toml` вручную; зависимости
   добавлять через `Pkg`.
2. Ввести минимальные модули с ясными границами: CLI, FASTA I/O, внешние
   процессы, discovery adapters, evaluation, comparison, pipeline и output.
   Не воспроизводить Python-классы механически: использовать функции,
   `NamedTuple`/простые неизменяемые `struct` и multiple dispatch только там,
   где он выражает реальную вариацию инструмента.
3. Определить единственный внутренний контракт discovery: входные пути FASTA,
   output directory, число мотивов и именованные параметры; выход --
   упорядоченный вектор моделей Mimosa.jl. Адаптер не изменяет модель вручную,
   кроме имени и проверяемых метаданных.
4. Изолировать побочные эффекты: запуск программ, чтение/запись файлов,
   создание каталогов и логирование находятся на границах; parameter-grid,
   выбор мотивов и фильтрация сравнений остаются чистыми функциями.
5. Настроить JuliaFormatter (BlueStyle), `Test`, Aqua.jl и JET.jl в
   development/test окружении; добавить CI для поддерживаемой версии Julia.

Критерий выхода: пустой, но устанавливаемый пакет имеет быстрый test suite,
format/lint/type-stability checks и не тянет Python toolchain.

## 4. Перенести общую логику и модели

1. Реализовать FASTA I/O и Jstacs-аннотированный FASTA с тестами на пустые,
   одиночные, множественные и пользовательски аннотированные последовательности.
2. Реализовать разрешение путей к внешним программам с прежним приоритетом:
   CLI override, environment variable, PATH/bundled artifact, затем понятная
   ошибка. Выполнять команды через Julia `Cmd` без shell interpolation и
   сохранять stdout/stderr в диагностике ошибки.
3. Перенести evaluation: best-site/all-site scores, AUROC, AUPRC, частичные
   AUROC/AUPRC и сохранение statistics в согласованном месте модели или
   отдельной записи результата -- в зависимости от подтверждённого API
   Mimosa.jl.
4. Перенести comparators и их семантику: `score`/`p-value`, inclusive
   threshold, направление сортировки, обязательный `adj.p-value`, matrix/PFM
   fallback и профильные метрики.
5. Перенести чистые части pipeline: odd/even split с 1-based смыслом,
   Cartesian parameter grid, локальную по параметрам дедупликацию,
   сопоставление fold-мотивов, выбор full-data мотива и глобальную дедупликацию.

Критерий выхода: тесты на selection/evaluation/comparison проходят только в
Julia и совпадают с зафиксированным baseline в пределах принятой политики.

## 5. Перенести bootstrap и воспроизводимость

1. Сформировать явные задания bootstrap с неизменяемыми входами: параметрами,
   fold, отдельным output directory и seed.
2. Сохранить текущую семантику deterministic seed: при заданном базовом seed
   задания получают устойчивые разные seed; без seed не создаётся ложная
   детерминированность.
3. Выбрать один прозрачный механизм параллельности Julia после benchmark и
   проверки внешних инструментов: `Distributed` для независимых процессов либо
   `Threads` только для thread-safe кода. Не распараллеливать stateful внешний
   SiteGA внутри одного запуска.
4. Ограничить параллелизм единым бюджетом `--jobs`; адаптеры передают один
   внутренний поток внешним программам, когда это поддерживается.
5. Сравнить последовательный и параллельный режимы на одинаковом seed и
   fixtures, включая стабильный порядок результатов.

Критерий выхода: parallel execution не меняет итоговый выбор при фиксированном
seed и не оставляет общих временных файлов между заданиями.

## 6. Перенести внешние discovery adapters

1. Перенести STREME и MEME: точные аргументы, нормализацию MEME text report,
   строгую фильтрацию по длине и чтение через Mimosa.jl.
2. Перенести BaMM: STREME initialization, порядок модели, входной `.ihbcp` и
   проверку наличия каждого ожидаемого файла.
3. Перенести Dimont и SlimDimont: генерацию Jstacs FASTA, Java command, memory
   limit, JAR resolution, параметры Jstacs, поиск XML и чтение через Mimosa.jl.
4. Решить хранение JAR: либо versioned Julia artifact, либо явно внешняя
   зависимость. Выбрать один вариант и документировать установку; не хранить
   непроверяемые бинарные копии в исходниках без контроля версии.
5. Для каждого адаптера сохранить unit tests на построение команды и parser,
   а настоящий запуск оставить отдельным opt-in integration test.

Критерий выхода: каждый не-SiteGA инструмент запускается из Julia на малом
fixture, возвращает модели Mimosa.jl ожидаемой длины и проходит opt-in smoke
test при наличии бинарной зависимости.

## 7. Адаптировать `SitegaDiscoveryTool`

1. Зафиксировать внешний SiteGA CLI/API как часть межпроектного контракта.
   Минимальные входы: foreground/background FASTA, output directory, motif
   `length`, `lpd`, requested motif count, seed и допустимый бюджет потоков.
   Дополнительные algorithm-specific параметры остаются собственностью SiteGA,
   а не скрытыми настройками MotifHORDE.
2. Требовать от SiteGA manifest в стабильном текстовом формате (например JSON):
   schema/version, status, diagnostic message, seed, упорядоченный список
   модельных файлов, model type, длина и имя. Не извлекать смысл из имён вроде
   `*_mat1` и не переименовывать файлы в обход SiteGA.
3. Реализовать `SitegaDiscoveryTool` как тонкий process adapter: собрать `Cmd`
   без shell, передать явно задокументированные параметры, проверить exit code
   и manifest, прочитать перечисленные модели Mimosa.jl, проверить type/length,
   присвоить стабильные имена и ограничить результат requested count.
4. Поддержать конфигурацию executable через CLI flag и environment variable в
   том же порядке приоритета, что и другие внешние инструменты. Отсутствующий
   executable или несовместимый manifest должны завершаться диагностической
   ошибкой, а не пустым результатом.
5. Добавить contract tests с fake SiteGA executable: успешный один/несколько
   мотивов, порядок, seed, thread budget, неподходящая длина, отсутствующий или
   некорректный manifest и ненулевой exit code. Добавить отдельный opt-in test
   против реального независимого проекта SiteGA после его готовности.

Критерий выхода: MotifHORDE запускает готовый Julia SiteGA как внешнюю
программу, не импортирует его исходники и не содержит ни одной строки C++.

## 8. Перенести CLI, сохранение и документацию

1. Реализовать CLI с существующими позиционными аргументами и параметрами,
   включая `streme`, `meme`, `bamm`, `dimont`, `slim`, `sitega`, range syntax,
   `--jobs`, comparator options и проверку недопустимых комбинаций.
2. Сохранять совместимую структуру каталогов и JSON statistics. Формат
   сериализованных моделей выбрать из stable format Mimosa.jl и обозначить
   расширением, не маскируя Julia-артефакты под Python `.pkl`.
3. Продолжить экспорт общего MEME PFM для downstream PWM-инструментов; для
   непозиционных моделей получать PFM только через подтверждённую функцию
   Mimosa.jl.
4. Перенести структурированные события verbose-лога и чётко описать любые
   намеренные изменения текста/путей в migration guide.
5. Переписать README, installation guide, environment definition и примеры
   под Julia; отдельно указать системные зависимости MEME Suite, BaMMmotif,
   Java/Jstacs и независимый SiteGA.

Критерий выхода: documented Julia command воспроизводит полный workflow и
создаёт понятные, переносимые результаты без Python runtime.

## 9. Проверить cutover и удалить legacy-код

1. На migration branch выполнить Julia unit suite, Aqua/JET проверки и
   integration tests с fake external tools. После удаления Python-кода
   повторить весь набор в чистом Julia-окружении.
2. Выполнить opt-in real-data smoke tests на первых 400 FASTA records для
   STREME, SlimDimont и готового внешнего SiteGA. Для каждого инструмента
   сохранить отдельный verbose log с командой, exit code, stdout и stderr.
   Это проверка интеграции, а не биологический benchmark.
3. Сверить Julia и Python baseline на общей матрице fixtures: split/seed,
   parameter sets, statistics, selection, final PFM и ошибки валидации.
4. После прохождения parity и SiteGA contract tests удалить в одном
   контролируемом изменении Python package, `setup.py`, `pyproject.toml`,
   `uv.lock`, Python tests, `src/sitega/`, compiled SiteGA modules, Python
   build/test инструкции и любые compatibility/fallback paths. Не удалять C++
   раньше, чем новый адаптер работает против согласованного релиза SiteGA.
   Проверить, что рабочее дерево после удаления собирается, тестируется и
   запускает весь поддерживаемый workflow только на Julia.
5. Удалить устаревшие ссылки на `mimosa-tool`, `joblib`, `pybind11`, C++17 и
   `sitega.train`; обновить CI, README, AGENTS.md и release notes. Оставить
   migration guide для старых Python outputs с требованием регенерации.

Критерий завершения и единственное условие релиза: репозиторий является
устанавливаемым Julia-пакетом; runtime, build и тесты не содержат и не требуют
Python/C++; отсутствуют legacy/compatibility paths; все поддерживаемые
discovery tools работают через явные адаптеры, а SiteGA подключается только
как отдельный Julia-проект по versioned process contract.

## Решения, которые нельзя откладывать до cutover

- Минимальная версия Julia и политика поддержки платформ.
- Версия/ревизия Mimosa.jl и набор поддерживаемых им model formats.
- Stable interchange format для моделей вместо Python pickle.
- Формат, versioning и ownership SiteGA manifest/CLI.
- Способ поставки Dimont/SlimDimont JAR.
- Численные tolerances и допустимый уровень различий результатов.
- Формальная проверка отсутствия Python/C++ и любых legacy paths перед первым
  Julia-релизом.
